# Upstream 2.0.0 adoption plan (PRO-7321)

Status as of 2026-09-03: upstream's latest tag is `2.0.0-rc4`. **2.0.0 is
not GA.** This document is the plan to *evaluate* it when it ships, and the
gate for actually adopting it — it is not itself a migration, and none of
its checklists are expected to be checked off yet.

## Why this is a plan and not a migration

A major-version bump is exactly the kind of change that shouldn't be done
reactively under ticket pressure: it can touch every native surface we've
patched (`patches/1.7.0/`, see `SERIES.md`) and the CC-side driver that
wraps the SDK. Deciding *whether* to adopt 2.0.0 at all is a real go/no-go,
not a foregone conclusion — see "Estimate & decide" below.

## Trigger

Re-open this plan (as a fresh ticket, referencing this file) when either:

- upstream tags a non-RC `2.0.0` release, or
- the drift-check workflow (`.github/workflows/upstream-drift-check.yml`)
  files an `upstream-drift` issue whose latest stable tag is `2.0.0` or
  later.

## 1. Breaking-change surface assessment

Read upstream's `CHANGELOG.md` and migration notes for every `2.0.0-rc*` /
`2.0.0-preview.*` tag between `1.7.0` and the GA tag, and check each
against:

- **`TwilioRNVoiceDriver` / `VoiceDriver`** (cc-mob-app:
  `src/voice/twilio/TwilioRNVoiceDriver.ts`, `src/voice/twilio/index.ts`,
  `src/voice/twilio/voice.ts`, `src/voice/twilio/audio.ts`,
  `src/voice/twilio/callStats.ts`, `src/voice/twilio/errors.ts`) — does the
  public JS API surface it calls (event names/payloads, method signatures,
  error codes) still match? cc-mob-app's own
  `TwilioRNVoiceDriver.contract.test.ts` and
  `TwilioRNVoiceDriver.conformance.test.ts` are the concrete spec to run
  this against once a 2.0.0 build exists.
- **Native `modules/cc-voip` glue** (cc-mob-app: `modules/cc-voip/ios/`,
  `modules/cc-voip/android/` where present) — anything that reaches into
  the SDK's native types (CallKit/PushKit bridging on iOS, the
  `VoiceService`/`MediaPlayerManager` surface on Android) needs re-checking
  against 2.0.0's native API, independent of the JS-level contract.
- **Expo config plugin** (`plugin/index.js`, `app.plugin.js`) — confirm the
  background modes / permissions / service declarations it emits are still
  what 2.0.0's native module manifests expect.

Produce a short table: upstream change -> affected file(s) above -> "no
action" / "adapt" / "blocked."

## 2. Patch-absorption check

Walk `patches/1.7.0/SERIES.md` patch by patch against upstream 2.0.0.
For each: **absorbed** (upstream now does this natively — drop the patch),
**still needed** (carry it forward, rebase it), or **superseded-but-different**
(upstream solved the same problem differently — needs a rewrite, not a
straight rebase). Update the "Still needed after upstream 2.0.0?" column in
`SERIES.md` with the verdict. Every patch that upstream absorbs is one less
thing we maintain — that's the main financial case for adopting a major
bump at all.

## 3. Estimate & decide

- Rough the engineering cost: rebase effort (informed by step 2), native
  build/config changes, cc-mob-app driver changes, QA surface (conformance
  suite + real-device PSTN smoke, see Part B of the ticket).
  Rough scale of "big" vs "small" test buckets:
  - **native SDK / driver contract change** -> full conformance suite +
    real-device smoke required, budget accordingly.
  - **CC-patch-only churn** (e.g. only the Android ringer-mode or ringback
    patches need rework) -> conformance suite still required, but the
    real-device smoke can likely stay scoped to inbound-call scenarios.
- State a recommendation: adopt now / adopt after upstream does X / stay on
  1.7.0-based patch series and keep only cherry-picking fixes (this is what
  the companion ticket PRO-7320 does for the near term). Get sign-off
  before starting the rebase.

## 4. Adoption gate

Do not merge a 2.0.0 rebase to `main` until **all** of:

- [ ] Upstream tag is `2.0.0` GA — not an `-rc*` / `-preview.*` tag.
- [ ] `patches/2.0.0/` series (produced by `scripts/rebase-patches.sh 2.0.0`)
      applies cleanly and reproduces an intentional tree (i.e. every diff
      from a straight upstream 2.0.0 checkout is an accounted-for CC patch,
      not an accidental conflict-resolution artifact).
- [ ] cc-mob-app's `TwilioRNVoiceDriver` conformance suite is green against
      an app built with the rebased fork.
- [ ] A real-device PSTN voice smoke (cc-mob-app `.maestro-real-device/`)
      passes: outbound call, inbound call while backgrounded (VoIP push ->
      CallKit), mid-call audio route change.

Only after all four does the SHA pin bump in cc-mob-app go out as a normal
release (see README "Keeping this fork current" for the mechanics, and
factory lessons L1759/L1760/L1766/L1767 for why the pin must point at a
post-squash `main` commit, never an open PR/branch head, and why a
native-only bump needs its own gated promotion rather than riding an
ordinary develop merge).
